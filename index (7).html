01

The problem: activity is not progress

Every automation team eventually hits the same wall. Requests multiply, bots go live, people are busy — and leadership still can't answer three simple questions: what is actually moving, what is stuck, and what do you need from us?

Symptom

"80% done" for months

Progress reported as a feeling or as code written. Near-complete initiatives sit near-complete indefinitely, because nobody defined what evidence closes them.

Symptom

Published ≠ healthy

A bot is "in production" — but nobody has looked at its last job. Deployment evidence gets confused with operational evidence.

Symptom

Knowledge lives in people

Owner unclear, repository unclear, design docs scattered. The portfolio is only understandable while one specific person remembers it.

A portfolio isn't managed by reporting activity. It's managed by evidence, gates and explicit decisions.

So I stopped reporting what the team did and started reporting what changed: which gates were crossed, on what evidence, what is blocked and by whom — and which decisions leadership needs to take to unlock the next gate. The rest of this page is how that system works.

The control model — three layers, one truth

Three layers with a single job each, so no number in front of leadership is ever a manual re-typing of another number. Every figure on a slide can be traced back to a row, and every row back to a repository and a runtime log.

Layer 1 · Single source of truth

Portfolio control workbook

One row per initiative. Updated in five minutes; everything downstream recalculates.

  • Status & business area
  • 7 delivery-gate scores
  • Named owner · action owner
  • Where it stopped · risks · next step
  • Next follow-up date · last update

Measuring maturity honestly

Maturity is the average of seven delivery gates, each scored on evidence: 1.0 confirmed · 0.5 partial · 0 not started. It is deliberately not a percentage of code written. Try it — click any gate to cycle its score.

Measured on exactly the initiatives presented at the previous review, with the same seven gates. This is the number that answers "did the portfolio move?" — without new entries diluting it or flattering it.

Why it matters in the roomThe portfolio grew from 19 to 24 initiatives in one cycle. Reported naively, average maturity dropped — and the first question from leadership would have been "what went wrong?". Separating the comparable basis from the full portfolio turns the same data into the right message: scope increased, but uncertainty decreased.

07

Decisions not to build

A mature portfolio is visible in what it refuses to do. In a single cycle, discovery drew four boundaries — before any effort was spent on low-value or redundant automation.

ClarifiedClosed

Two requests, one name

Two requests with the same name turned out to be separate processes in two departments. Split cleanly; the broader analytical need routed to a cross-functional decision-support initiative.

→ no duplicated build
Stop or re-scopeDecision gate

The workbook already does the maths

Discovery showed the existing workbook already held the calculation logic; a bot would only refresh source data. Limited value — and the same discovery surfaced a stronger opportunity elsewhere in the closing process.

→ build avoided · better candidate found
PausedDecision gate

The ERP may already solve it

An AI-assisted service was separated from an unrelated reporting request, and build work was paused once a native ERP solution was found that may already cover the need.

→ resume · re-scope · close on coverage evidence
RetiredBusiness call

Switched off — not failed

A production monitor was disabled at the business's request. Reported as a business decision, with retirement scope to document — so "published went from 5 to 4" never reads as a delivery failure.

→ confirm permanent retirement
The principleThe goal is not the highest robot count. It's the right solution for a justified business need — and sometimes that solution is a spreadsheet that already exists, or a native feature someone else is shipping.

Four things leadership gets from this system that it didn't have before — each one with a mechanism behind it, not a slogan.

Governance

named-owner coverage · one review cycle

Every open item has an owner and a date

  • One next step, one action owner and one follow-up date per initiative
  • Follow-up triggers defined for 16 of 24 — a control that didn't exist before
  • Structural questions framed as a prioritised backlog for the global owner
Traceability
5 dimensions
tracked per initiative, end to end

Transferable without anyone's memory

  • Portfolio issue · canonical repository · key-user discovery · design doc · full alignment
  • Gaps shown openly: 5 of 24 fully aligned today, with a plan to close the rest
  • The test: anyone can pick up any initiative from its trail alone

  • Cost avoidance made explicit: low-value and redundant builds stopped before effort was spent
  • "Reuse before rebuild" — existing analytics treated as assets, not replaced

Visibility is only the beginning. The real deliverable is conversion — every open gate with an owner, an evidence path and a decision date, reviewed by the people who can actually unblock it.
